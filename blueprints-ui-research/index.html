A visual Blueprints editor — and 6 ways it could look

Research into everything the team has said about a Blueprint UI, a survey of how comparable products handle “config-as-code that also needs a friendly face,” the progressive-disclosure patterns that make users happy without capping developers — and six clickable design directions to react to, led by a “bill of materials.”

The short version

Model the Blueprint the way a user pictures their site — a bill of materials: “these plugins, this theme, this content, these people.” Each category is a list with a ＋ — not one card per item, and never a label that echoes the schema. Keep a Custom code category as the escape hatch, let power users flip the whole thing to synced raw JSON, and build it correct-by-construction (the UI can only emit valid Blueprints) with lenient validation. Two research passes plus the team's own history point here; v2's declarative shape makes it click.

How they map

The five aren't mutually exclusive — they sit at different points on the “speaks-the-user's-language ↔ full-developer-power” axis and can compose.

🙂 Speaks the user's language ⚙️ Full developer power 3 · Guided 4 · AI 6 · BOM ★ 1 · Cards 5 · Notebook 2 · Form⇄Code
The move that satisfies both ends at once: a per-field / per-card escape hatch — friendly value 90% of the time, raw PHP / wp-config / expression the other 10% — plus a global Simple / Advanced mode. That's how one editor serves a first-timer and a core contributor without either feeling out of place.

What the research turned up

Full detail (with every link and quote) is in README.md. The headlines:

🏛️ This has a 3-year history — and 8+ builders

  • Adam's 2023 Coordination Thread exists precisely to avoid re-building the same thing; that fear largely came true.
  • Prior art: Alex Kirk's Step Library (65+ macro steps that compile to primitives), lubusIN's block-based builder, Sean Morris / Sejas builder.html, jdevalk's site→Blueprint exporter, plus AI-generation work across wpcom / Studio / Big Sky.
  • A real editor is shipping right now in the 2026 Dock UI — this branch. A visual layer slots in over the same blueprint.json.

“The step library makes perfect sense in Gutenberg. Custom steps would be just custom blocks… predefined sites with customizable parts are just partially-synced patterns.” — Adam

🧭 The team already agrees on the shape

  • Two-tier UX: friendly visual layer + raw-JSON escape hatch (“simple / advanced mode”). Near-universal.
  • Correct-by-construction: the UI should only produce valid Blueprints (Dennis Snell).
  • Lenient validation like a browser: run valid steps, warn on the rest (Francesco Bigiarini).
  • Inline editing in the canvas, not a detached inspector — Adam: moving inputs away is “friction.”
  • Open debates: AI-first vs manual, and where it lives (Add-Site form vs Settings vs companion).

🔭 What comparable products do

  • Gutenberg — list view + inspector + “Edit as HTML” over an ordered list of typed items. Almost literally a Blueprint.
  • Stoplight / GitLab CI — form ⇄ code with jump-to-node + a “merged/full config” lens.
  • n8n — per-field value ⇄ expression toggle with a live preview; the single most transferable control.
  • Local / Vercel / Shopify — Preferred-vs-Custom fork, detect-and-prefill, setup checklist.

🪆 Progressive-disclosure patterns that fit

  • Layered “Advanced” reveal — sensible defaults hidden until needed (NN/g: never exceed 2 levels).
  • Semantic macro steps — outcome-named steps that compile to primitives (Alex Kirk), with “expand to primitives” as the door out of a leaky abstraction.
  • Escape hatch — a runPHP cell in the same list; devs never hit a wall.
  • Status dots on collapsed cards so nothing important hides silently.

Anti-patterns to dodge: destructive mode-switch, formatting churn, “Advanced” junk-drawer, escape-hatch overuse.
