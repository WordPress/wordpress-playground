# Create a one-click bug or pull-request reproduction

A useful reproduction gives every reviewer the same runtime, code, data, and
starting URL. Blueprint v2 can make that test case one click in a browser and
the same committed fixture can run headlessly in CI.

## What you will build

- A pinned WordPress, PHP, and plugin test matrix.
- Minimal content that states one expected and one actual result.
- A visible environment marker generated by a small inline mu-plugin.
- A share URL that starts the fixture directly in Playground.
- A headless command suitable for a pull request or continuous integration.

## Prerequisites

- A minimal sequence that reproduces the behavior on a fresh site.
- Exact released versions, or the full commit SHA of code under review.
- A public, CORS-readable URL if reviewers will load the JSON in a browser.
- Node.js for local and CI execution with the Playground CLI.

## Run the finished reproduction fixture

Run the same checked fixture used by this page.

```json blueprint-v2 fixture=bug-reproduction
{
	"$schema": "https://playground.wordpress.net/blueprint-schema.json",
	"version": 2,
	"blueprintMeta": {
		"name": "Bug reproduction",
		"description": "A pinned, one-click environment for reporting a WordPress bug or reviewing a pull request.",
		"authors": ["WordPress Playground"],
		"tags": ["bug", "reproduction", "testing"]
	},
	"applicationOptions": {
		"wordpress-playground": {
			"landingPage": "/bug-reproduction/",
			"login": false,
			"networkAccess": false
		}
	},
	"contentBaseline": "empty",
	"phpVersion": "8.3",
	"wordpressVersion": "6.8.3",
	"constants": {
		"WP_DEBUG": true,
		"WP_DEBUG_DISPLAY": true,
		"SCRIPT_DEBUG": true
	},
	"plugins": [
		{
			"source": "hello-dolly@1.7.2",
			"active": true,
			"ifAlreadyInstalled": "skip"
		}
	],
	"muPlugins": [
		{
			"filename": "reproduction-environment.php",
			"content": "<?php\n/**\n * Plugin Name: Reproduction environment\n */\nadd_shortcode( 'repro_environment', function () {\n\treturn '<dl><dt>WordPress</dt><dd>' . esc_html( get_bloginfo( 'version' ) ) . '</dd><dt>PHP</dt><dd>' . esc_html( PHP_MAJOR_VERSION . '.' . PHP_MINOR_VERSION ) . '</dd></dl>';\n} );\n"
		}
	],
	"siteOptions": {
		"blogname": "Bug reproduction",
		"permalink_structure": "/%postname%/"
	},
	"content": [
		{
			"type": "posts",
			"source": {
				"post_title": "Bug reproduction",
				"post_name": "bug-reproduction",
				"post_type": "page",
				"post_status": "publish",
				"post_content": "<!-- wp:heading {\"level\":1} --><h1 class=\"wp-block-heading\">Bug reproduction</h1><!-- /wp:heading --><!-- wp:shortcode -->[repro_environment]<!-- /wp:shortcode --><!-- wp:columns --><div class=\"wp-block-columns\"><!-- wp:column --><div class=\"wp-block-column\"><!-- wp:heading {\"level\":2} --><h2 class=\"wp-block-heading\">Expected</h2><!-- /wp:heading --><!-- wp:paragraph --><p>Replace this text with one observable expected result.</p><!-- /wp:paragraph --></div><!-- /wp:column --><!-- wp:column --><div class=\"wp-block-column\"><!-- wp:heading {\"level\":2} --><h2 class=\"wp-block-heading\">Actual</h2><!-- /wp:heading --><!-- wp:paragraph --><p>Replace this text with what actually happens.</p><!-- /wp:paragraph --></div><!-- /wp:column --></div><!-- /wp:columns -->"
			}
		}
	]
}
```

[Run in Playground](https://playground.wordpress.net/?blueprint-url=https://raw.githubusercontent.com/WordPress/wordpress-playground/refs/heads/trunk/packages/docs/site/src/examples/blueprints-v2/bug-reproduction.json)

Use the code block's copy action to copy or save the declaration. In Playground,
open **Dock → Blueprint** to inspect or edit it.

The finished run opens `/bug-reproduction/`. It reports WordPress 6.8.3 and the
PHP 8.3 runtime line, activates Hello Dolly 1.7.2, and displays side-by-side
**Expected** and **Actual** sections. The text is deliberately neutral: replace
it and the example dependency with the smallest state that exposes the real
problem.

## 1. Pin every input that defines the result

The fixture uses an exact WordPress release and plugin release:

```jsonc
"phpVersion": "8.3",
"wordpressVersion": "6.8.3",
"plugins": [
	{
		"source": "hello-dolly@1.7.2",
		"active": true,
		"ifAlreadyInstalled": "skip"
	}
]
```

Do not use `latest`, a moving branch, or an unversioned WordPress.org slug in a
long-lived bug report. Those inputs can change without changing the JSON.

For a plugin or theme built directly from Git, use the full commit SHA:

```jsonc
"plugins": [
	{
		"source": {
			"gitRepository": "https://github.com/acme/example-plugin",
			"ref": "4f86d3f04b47e86a9802a58e6c7aef2f3cb92f55",
			"pathInRepository": "plugin"
		},
		"targetDirectoryName": "example-plugin",
		"active": true
	}
]
```

A pull-request ref is convenient while a review is moving, but it is mutable.
Record the full head commit in a reproduction that must still mean the same
thing after the pull request changes or closes. Git sources install committed
files only; point to a built artifact when the project requires a build step.

## 2. Declare only representative state

The fixture removes default content, turns on debug constants, creates one
page, and registers one inline shortcode. This is enough to make the runtime
visible and keep the expected-versus-actual report beside the test content.

For a real issue:

1. Remove unrelated plugins, themes, options, users, and content.
2. Preserve the exact activation state that triggers the problem.
3. Use stable slugs and an explicit `landingPage`.
4. State one observable expected result and one observable actual result.
5. Keep any interaction after boot short enough to repeat in a review.

The inline mu-plugin is executable PHP. Use it only for setup that cannot be
expressed as ordinary site state, and keep it small enough to review in the
JSON. Use [additional tail steps](/blueprints/v2/reference/additional-steps)
only when the reproduction genuinely needs imperative work after declarations.

## 3. Commit the fixture and make a browser share URL

Host the JSON at an immutable URL. A raw GitHub URL should contain the full
commit SHA, not `main` or `trunk`:

```js
const blueprintUrl = 'https://raw.githubusercontent.com/acme/example-plugin/' + '4f86d3f04b47e86a9802a58e6c7aef2f3cb92f55/' + 'tests/bug-reproduction.json';

const shareUrl = 'https://playground.wordpress.net/?blueprint-url=' + encodeURIComponent(blueprintUrl);
```

Open `shareUrl` in a signed-out browser before posting it. The JSON and every
adjacent remote asset need normal browser fetch and CORS access. For private or
binary inputs, prefer an attached, reviewable bundle rather than embedding
credentials in a URL.

## 4. Run the same fixture headlessly

Execute it locally without starting a web server:

```bash
npx @wp-playground/cli@latest run-blueprint \
	--blueprint=./tests/bug-reproduction.json
```

Add that command to CI so schema, resource resolution, installation, and setup
fail the check when the fixture stops executing. Keep application-specific
assertions in a separate test so the Blueprint remains a readable declaration
of the environment.

Recommended CI fixture rules:

- Commit `blueprint.json` and every local input it references.
- Use exact WordPress.org versions and full Git commit SHAs.
- Grant `--blueprint-may-read-adjacent-files` only when a standalone JSON file
  intentionally reads sibling files; a directory or ZIP bundle does not need it.
- Run the repository's schema/example validator before the headless execution.
- Avoid network-dependent setup unless network behavior is itself under test.
- Update a pin in a reviewable commit rather than silently following a branch.

See [Run Blueprints v2](/blueprints/v2/run) for browser, CLI, and JavaScript
entry points.

## Security and failure reporting

A reproduction can install and execute arbitrary plugin, theme, mu-plugin, PHP,
SQL, or WP-CLI code. Review the fixture before running it, use a temporary site,
and never store secrets in JSON or a share URL. The example keeps
`networkAccess: false`; enable it only when outbound access is essential to the
bug.

Blueprint execution is not transactional. If it fails halfway through, report
the failing phase and source path, then retry on a fresh site. The
[troubleshooting guide](/blueprints/v2/troubleshooting) follows the parse,
validate, resolve, and execute phases in order.
